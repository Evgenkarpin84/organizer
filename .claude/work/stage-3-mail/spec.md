# Спецификация: этап 3 — сбор почты и экран «Почта»

Статус: критерии приёмки заморожены 23.09.2026. Всё новое сверх них — в `BACKLOG.md`.

## 1. Цель и рамки

Цель: письма из четырёх ящиков (три на Mail.ru, один на Яндексе) попадают в Supabase скриптом на ПК, а вкладка «Почта» вместо заглушки показывает их списком, даёт открыть письмо, отметить прочитанным, убрать в архив и создать из письма задачу через существующий редактор задач.

Входит:
- скрипт `scripts/fetch-mail.mjs`: IMAP по паролям приложений из `.env`, инкрементальная догрузка по UID, дедупликация, обрезка текста, запись в Supabase под сервисным ключом;
- режимы `--check` (проверка настроек без сети) и `--dry-run` (чтение без записи в базу), понятные сообщения об ошибках подключения;
- миграция `supabase/migrations/0003_mail.sql`: таблицы `mail_accounts` и `mail_messages` с RLS — как файл в репозитории;
- фронтенд: вкладка «Почта» (список с группировкой по дате или по ящику, фильтры), экран письма `/mail/:id`, действия «прочитано», «в архив», «создать задачу»;
- чистые функции разбора заголовков, выбора текстовой части, дедупликации, обрезки и отбора новых писем — с тестами Vitest без сети и почтового сервера;
- документация в `README.md`, переменные в `.env.example`.

Не входит (этап 3b, см. раздел 12):
- **применение миграции к реальному проекту и первый запуск скрипта к живым ящикам** — только файлы в репозитории, запуск делает пользователь отдельным шагом после подтверждения;
- разбор писем моделью: категории, приоритеты, краткие содержания, рекомендации;
- черновики ответов и отправка писем (любой вид `SMTP`);
- автоматическое создание задач из просьб в письмах;
- вложения: скачивание, хранение, просмотр — сохраняются только факт наличия и имена файлов;
- обратная синхронизация с ящиком: флаг `\Seen`, перемещение и удаление писем на сервере;
- папки кроме `INBOX` (Спам, Промоакции, «Отправленные»), поиск по письмам, пагинация «Показать ещё»;
- push-уведомления о новых письмах;
- журнал запусков скриптов `job_runs` (пункт бэклога, общий для этапов 3–5).

Отступление от шаблона: критериев 12, а не 7. Этап неделим — скрипт без таблицы и экрана не проверяется, экран без скрипта пуст, — а форма списка повторяет спеки этапов 0–1 и 2 с пометками способа проверки.

## 2. Критерии приёмки

Проверка: `А` — автоматически (сборка, типы, тесты, линтер, поиск по файлам), `Р` — вручную в браузере на ПК, `Б` — только на живых данных (применённая миграция `0003` + реальные ящики).

- AC1 (А). `npm run build`, `npm run typecheck`, `npm run lint`, `npm test` проходят без ошибок. Тесты не обращаются к сети, IMAP и Supabase: в тестовых файлах нет `ImapFlow`, `fetch(`, `requireSupabase` и `createClient`; работа с базой и почтой проверяется только на подставных объектах.
- AC2 (А). `scripts/mail/config.mjs` — чистые функции с тестами: `parseAccounts(env)` собирает из переменных `MAIL_1_*`…`MAIL_8_*` список ящиков (три `mailru` и один `yandex` в тестовом наборе), подставляет хост и порт по провайдеру (`imap.mail.ru:993`, `imap.yandex.ru:993`, TLS), папку `INBOX` по умолчанию и метку по умолчанию из адреса; при пропущенном пароле или неизвестном провайдере возвращает ошибку на русском с именем переменной; ни одно сообщение об ошибке не содержит значения пароля. `parseArgs` распознаёт `--check`, `--dry-run`, `--account=<key>`, `--limit=<N>`.
- AC3 (А). `scripts/mail/message.mjs` — чистые функции с тестами: `dedupeKey` берёт нормализованный `Message-ID` (без угловых скобок, в нижнем регистре), а без него — sha256 от ящика, UID, даты и темы; `fetchRange(state, options)` при известном `last_uid` даёт диапазон `last_uid+1:*`, при смене `uid_validity` сбрасывает состояние и ограничивает добор окном `MAIL_BACKFILL_DAYS` (по умолчанию 30 дней), первый запуск ящика тоже ограничен этим окном и `MAIL_MAX_PER_RUN` (по умолчанию 200 писем на ящик за запуск).
- AC4 (А). Ограничения на объём и приватность покрыты тестами: `pickTextPart(bodyStructure)` предпочитает `text/plain`, затем `text/html`, пропускает части с `disposition: attachment` и части больше 256 КБ, а при их отсутствии возвращает `null`; `htmlToPlainText` вырезает `script`, `style` и теги, разворачивает базовые сущности и сжимает пробелы; `buildMessageRow` обрезает текст до 2000 символов (для рассылок — до 500), выставляет `body_truncated`, кладёт в `preview` не больше 200 символов, а из вложений сохраняет только `has_attachments` и до 10 имён по 120 символов; `isBulk` истинна при наличии `List-Unsubscribe`, `List-Id` или `Precedence: bulk`. HTML-версия письма в строку не попадает ни в каком поле.
- AC5 (А). Миграция `supabase/migrations/0003_mail.sql` создаёт таблицы `mail_accounts` и `mail_messages`, включает RLS и заводит по четыре политики (`select`, `insert`, `update`, `delete`) с условием `user_id = auth.uid()`; есть уникальные ограничения `mail_messages (user_id, dedupe_key)` и `mail_messages (account_id, uid)`, индексы под выборку списка по дате и по ящику, ограничения на длину `body_text` (≤ 4000) и `preview` (≤ 400). Скрипт идемпотентен: повторный запуск не падает. Схема задач и напоминаний не меняется.
- AC6 (А). `scripts/mail/store.mjs` — запись через переданный клиент, покрыта тестами с подставным клиентом: при `dryRun: true` не вызывается ни один метод записи (`insert`, `upsert`, `update`), а возвращается сводка «сколько писем было бы добавлено»; при `dryRun: false` письма уходят одним `upsert` с `onConflict: 'user_id,dedupe_key'` и `ignoreDuplicates: true`, то есть повторный запуск не перезаписывает уже сохранённое письмо и не сбрасывает `read_at` и `archived_at`; в каждой строке явно проставлен `user_id` из `OWNER_USER_ID`; состояние ящика (`uid_validity`, `last_uid`, `last_sync_at`, `last_error`) обновляется после успешной обработки, а при ошибке подключения в `last_error` пишется текст без пароля.
- AC7 (А). Экран «Почта» (`src/screens/MailScreen.tsx`) покрыт тестами компонента с подставленными данными: по умолчанию письма сгруппированы по дате («Сегодня», «Вчера», затем дата вида «15 сентября»), переключатель «По дате / По ящику» меняет группировку на заголовки с метками ящиков, фильтры «Все», «Непрочитанные», «Архив» показывают соответствующие наборы (архивные письма в «Все» не видны), непрочитанное письмо выделено и в шапке видно число непрочитанных, у письма с вложением видна иконка вложения, строка письма содержит отправителя, тему (или «Письмо без темы») и превью; пустые состояния «Писем пока нет» и «Ничего не найдено» имеют разный текст.
- AC8 (А). Экран письма `/mail/:id` открывается тапом по строке списка и покрыт тестами: показывает тему, отправителя, метку ящика, дату и сохранённый текст, а при `body_truncated` — подпись «Текст письма сохранён не полностью»; кнопки «Прочитано/Непрочитано» и «В архив/Из архива» переключают состояние и вызывают репозиторий один раз; кнопка «Создать задачу» ведёт на `/task/new` с черновиком, в котором название — тема письма (для письма без темы — «Письмо от <отправитель>»), а заметка содержит адрес отправителя и первые 500 символов текста; сам черновик собирает чистая функция `draftFromMail` с отдельным тестом.
- AC9 (А). Нижняя навигация по-прежнему состоит ровно из пяти вкладок, заглушки этапа 3 в `App.tsx` больше нет; маршруты `/mail` и `/mail/:id` работают в подкаталоге `/organizer/` (`HashRouter`, относительные пути сохранены); письма грузятся отдельным хуком только при открытии вкладки, а не в общем `DataProvider`, чтобы вкладка «Сегодня» не ждала почту; ошибки загрузки и записи показываются текстом на русском, экран остаётся работоспособным.
- AC10 (Б). На живых данных: `npm run mail -- --check` печатает четыре ящика и не обращается к сети; `npm run mail -- --dry-run` подключается ко всем четырём ящикам и сообщает количество новых писем, ничего не записав; `npm run mail` записывает письма, повторный запуск сразу после первого добавляет 0 писем; при неверном пароле приложения скрипт пишет понятную ошибку с меткой ящика и хостом, завершается кодом 1 и продолжает работу по остальным ящикам.
- AC11 (А). Секреты не утекают: в `.env.example` есть `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `OWNER_USER_ID`, `MAIL_1_*`…`MAIL_4_*`, `MAIL_BACKFILL_DAYS`, `MAIL_MAX_PER_RUN` с пустыми значениями и без префикса `VITE_`; поиск по `src/**` не находит ни `SERVICE_ROLE`, ни `MAIL_`, ни `IMAP`; собранный `dist` не содержит строк `SUPABASE_SERVICE_ROLE_KEY` и `imap`; фронтенд обращается к письмам только через `requireSupabase()` с публикуемым ключом и RLS.
- AC12 (А). `README.md` содержит раздел «Почта»: как получить пароли приложений на Mail.ru и на Яндексе (включая включение IMAP), таблицу переменных окружения, применение миграции `0003_mail.sql`, ручной запуск (`npm run mail`, `--check`, `--dry-run`, `--account=`), настройку расписания Windows одной командой `schtasks` с путём к журналу и способом отключения, а также раздел «Что хранится в базе» с пределами 2000/500 символов, отсутствием HTML и вложений.

## 3. Модель данных

Миграция `supabase/migrations/0003_mail.sql`.

`mail_accounts` — один ящик, его состояние синхронизации:
- `id uuid pk default gen_random_uuid()`
- `user_id uuid not null default auth.uid() references auth.users (id) on delete cascade`
- `key text not null` — идентификатор из `.env` (`mail1`…`mail8`), уникален в паре `(user_id, key)`
- `label text not null` — как ящик подписан в интерфейсе («Личная bk.ru»)
- `email text not null`
- `provider text not null check (provider in ('mailru', 'yandex'))`
- `folder text not null default 'INBOX'`
- `uid_validity bigint`, `last_uid bigint not null default 0` — точка инкрементальной загрузки
- `last_sync_at timestamptz`, `last_error text`
- `created_at timestamptz not null default now()`

`mail_messages` — письмо:
- `id uuid pk default gen_random_uuid()`
- `user_id uuid not null default auth.uid() references auth.users (id) on delete cascade`
- `account_id uuid not null references public.mail_accounts (id) on delete cascade`
- `uid bigint not null`, уникально в паре `(account_id, uid)`
- `dedupe_key text not null`, уникально в паре `(user_id, dedupe_key)`
- `message_id text`
- `subject text` (≤ 500), `from_name text`, `from_email text`, `to_emails text[]` (≤ 10 адресов)
- `sent_at timestamptz` (дата из конверта), `received_at timestamptz not null` (`internalDate`, по нему сортировка)
- `preview text` (≤ 400 по проверке в БД, ≤ 200 по правилу скрипта), `body_text text` (≤ 4000 по проверке в БД, ≤ 2000 по правилу скрипта), `body_truncated boolean not null default false`
- `has_attachments boolean not null default false`, `attachment_names text[] not null default '{}'`
- `is_bulk boolean not null default false`, `size_bytes integer`
- `read_at timestamptz` — при первой записи `now()`, если у письма в ящике стоит `\Seen`, иначе `null`
- `archived_at timestamptz`
- `created_at timestamptz not null default now()`

Индексы: `mail_messages (user_id, archived_at, received_at desc)`, `mail_messages (user_id, account_id, received_at desc)`, `mail_accounts (user_id, key)`.

RLS включена на обеих таблицах, по четыре политики с `user_id = auth.uid()`. Скрипт работает под `service_role` и RLS обходит, поэтому `user_id` в каждой строке подставляется явно из `OWNER_USER_ID` — значение по умолчанию `auth.uid()` под сервисным ключом пусто.

Типы фронтенда добавляются в `src/lib/types.ts`: `MailAccount` (`id`, `key`, `label`, `email`, `provider`, `lastSyncAt`, `lastError`) и `MailMessage` (`id`, `accountId`, `subject`, `fromName`, `fromEmail`, `sentAt`, `receivedAt`, `preview`, `bodyText`, `bodyTruncated`, `hasAttachments`, `attachmentNames`, `isBulk`, `readAt`, `archivedAt`).

## 4. Приватность и объём хранимого

1. Хранится только текст: `text/plain` как есть, `text/html` — после превращения в текст. Исходный HTML не сохраняется нигде.
2. Предел текста — 2000 символов. Для рассылок (`is_bulk`) — 500: в них смысла мало, а объём большой. Превышение отмечается `body_truncated`, полное письмо остаётся в ящике.
3. Вложения не скачиваются. По `bodyStructure` определяются флаг `has_attachments` и до 10 имён файлов; тела вложений по сети не запрашиваются вовсе — загружается ровно одна выбранная текстовая часть.
4. Текстовая часть больше 256 КБ не загружается: письмо сохраняется с пустым текстом, превью «Текст письма не сохранён (слишком большой)» и `body_truncated = true`.
5. Пароли приложений и сервисный ключ живут только в `.env`, в логи и в поле `last_error` не попадают: сообщения об ошибках чистятся от значений переменных окружения.
6. Папка только `INBOX`: Спам и Промоакции не читаются.

## 5. Устройство скрипта

```
scripts/fetch-mail.mjs      точка входа: разбор аргументов, .env, цикл по ящикам, IMAP, запись
scripts/mail/config.mjs     parseAccounts, parseArgs, readOptions — чистые
scripts/mail/message.mjs    dedupeKey, fetchRange, pickTextPart, htmlToPlainText, buildMessageRow,
                            isBulk, parseHeaderLines, attachmentNames — чистые
scripts/mail/store.mjs      loadAccounts, upsertMessages, saveAccountState — работа через
                            переданный клиент, с флагом dryRun
scripts/mail/*.test.mjs     тесты Vitest с явным import { describe, expect, it } from 'vitest'
```

Ход работы:
1. Разбор аргументов: `--check`, `--dry-run`, `--account=<key>`, `--limit=<N>`, `--verbose`.
2. Чтение `.env` через `process.loadEnvFile()` (Node 22) в `try/catch`; файла нет — понятное сообщение «Создайте .env из .env.example» и код выхода 1. Уже заданные переменные окружения имеют приоритет.
3. `parseAccounts` собирает ящики; при ошибках конфигурации печатается список проблем и код 1. Режим `--check` на этом и заканчивается: таблица «метка — адрес — провайдер — хост — папка», ни одного сетевого вызова.
4. Клиент Supabase создаётся на `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY` с `persistSession: false`; строки ящиков читаются или создаются (`mail_accounts` по `(user_id, key)`).
5. По каждому ящику: подключение `ImapFlow` (TLS, порт 993, таймаут 30 с), `INBOX` в режиме только для чтения (`mailboxOpen(folder, { readOnly: true })`) — флаги в ящике не меняются.
6. `fetchRange` даёт диапазон UID; `fetch` запрашивает `uid`, `flags`, `envelope`, `bodyStructure`, `internalDate`, `size` и нужные заголовки (`list-unsubscribe`, `list-id`, `precedence`) — без тела.
7. Для каждого письма `pickTextPart` выбирает часть, `download` тянет только её с ограничением по размеру, `buildMessageRow` собирает строку.
8. Партии по 50 строк уходят `upsert` с `ignoreDuplicates: true`; затем обновляется состояние ящика. В `--dry-run` вместо записи считается количество.
9. Итог: по каждому ящику «метка: новых N, пропущено дубликатов M» и общая сводка; ошибка одного ящика не срывает остальные, но итоговый код выхода 1. Ошибки подключения переводятся в понятный текст: неверный пароль или выключенный IMAP, недоступен хост, таймаут, отказ TLS.

## 6. Расписание Windows

Скрипт вызывается `npm run mail`, журнал — `logs\mail.log` (папка `logs/` в `.gitignore`). Регистрация задания раз в 30 минут:

```powershell
schtasks /create /tn "Органайзер: почта" /sc minute /mo 30 /f `
  /tr "cmd /c cd /d C:\newIDEA && npm run mail >> logs\mail.log 2>&1"
```

Разовый запуск для проверки — `schtasks /run /tn "Органайзер: почта"`, отключение — `schtasks /delete /tn "Органайзер: почта" /f`. Задание работает только при включённом ПК: это осознанное ограничение архитектуры («мозг» живёт на компьютере), в отличие от push-напоминаний из этапа 2.

## 7. Интерфейс

Вкладка «Почта» (`/mail`), вкладок в нижней навигации остаётся пять.

- Шапка экрана: число непрочитанных, переключатель группировки «По дате / По ящику» (выбор хранится в `localStorage`), чипсы фильтра «Все», «Непрочитанные», «Архив».
- Список: группы с заголовками; строка письма — метка ящика, отправитель, тема, превью в одну строку, время или дата, иконка вложения, точка непрочитанного. Высота строки достаточна для тапа (не меньше 44 px), mobile-first.
- Экран письма `/mail/:id`: тема, отправитель с адресом, метка ящика, дата, имена вложений, текст письма, подпись об обрезке; действия «Прочитано/Непрочитано», «В архив/Из архива», «Создать задачу», «Назад».
- Открытие письма ставит `read_at`, если он был пуст.
- «Создать задачу» открывает существующий редактор `/task/new` с черновиком в состоянии маршрута; сохранение идёт обычным путём `addTask`, новых способов создания задач не появляется.
- Данные грузит хук `useMail` при монтировании вкладки: последние 200 писем, изменения состояния применяются оптимистично, при ошибке возвращаются назад с сообщением.
- Новые иконки в `src/components/Icon.tsx`: `archive`, `clip`.

## 8. Стек и зависимости

Новая зависимость одна: **`imapflow`** — promise-based IMAP-клиент, поддерживает выборку по UID, `bodyStructure`, скачивание отдельной части (`download`) с декодированием transfer-encoding и charset, разбор конверта с раскодированными MIME-заголовками. Этого достаточно и для «разбора писем»: тема и адреса приходят уже декодированными, а HTML в текст превращает своя чистая функция.

Отклонено:
- **`mailparser` / `simpleParser`** — работает с полным исходником письма, то есть тянет по сети вложения целиком, что прямо противоречит разделу 4;
- **`node-imap` / `imap-simple`** — колбэчный API и слабая поддержка;
- **`dotenv`** — не нужен: Node 22 умеет `process.loadEnvFile()`;
- **`html-to-text`** — задача решается двадцатью строками чистой функции, которую всё равно надо покрывать тестом.

Supabase — уже подключённый `@supabase/supabase-js` (работает и в Node). Фронтенд новых пакетов не получает. Тесты гоняет существующий Vitest: в `vite.config.ts` в `test.include` добавляется `scripts/**/*.test.mjs`; тесты импортируют `describe`/`it`/`expect` из `vitest` явно, чтобы блок ESLint для `scripts/**/*.mjs` не ругался на неизвестные глобальные переменные. `tsconfig.json` не меняется (`scripts` уже включён, `checkJs` выключен).

## 11. Принятые допущения

1. Ящик только читается: `mailboxOpen` с `readOnly: true`, флаги на сервере не меняются. «Прочитано» и «архив» — состояния внутри органайзера; в почтовом клиенте письмо остаётся как было.
2. Папка одна — `INBOX`. Спам и Промоакции не забираются, иначе база быстро заполнится мусором.
3. Первый запуск ящика берёт письма за 30 дней и не больше 200 за запуск; остальное просто не попадает в органайзер (историю не выгружаем).
4. Текст письма хранится обрезанным: 2000 символов, для рассылок 500. HTML не хранится вообще, письмо целиком всегда доступно в почтовом клиенте.
5. Вложения не скачиваются: сохраняются флаг и до 10 имён файлов.
6. Дедупликация по паре `(user_id, dedupe_key)`: `Message-ID`, а при его отсутствии — sha256 от ящика, UID, даты и темы. Дополнительно уникальна пара `(account_id, uid)`.
7. Инкрементальность — по UID: хранятся `uid_validity` и `last_uid`, при смене `uid_validity` состояние сбрасывается, а от дублей спасает `dedupe_key`.
8. `user_id` подставляется скриптом из `OWNER_USER_ID`: под сервисным ключом `auth.uid()` пуст, значение по умолчанию не сработало бы.
9. Провайдер задаётся ключевым словом (`mailru`, `yandex`), хост и порт выводятся из него; произвольные IMAP-серверы не поддерживаются — у владельца ящики только этих двух провайдеров.
10. Требуется Node 22: `.env` читается встроенным `process.loadEnvFile()`, зависимость `dotenv` не добавляется.
11. Одна новая npm-зависимость — `imapflow`; `mailparser` отклонён, потому что требует полный исходник письма и потянул бы вложения.
12. Письмо открывается маршрутом `/mail/:id` внутри приложения; пятёрка вкладок нижней навигации не меняется (AC6 этапов 0–1).
13. Список — последние 200 неархивных писем; пагинации «Показать ещё» нет, при росте объёма это пункт бэклога.
14. Группировка по дате — по умолчанию, «по ящику» — переключатель; выбранный режим и фильтр хранятся в `localStorage`.
15. Связи «письмо ↔ задача» в базе нет: из письма создаётся обычная задача, обратной ссылки и отметки «задача создана» на этом этапе не будет.
16. Скрипт запускается только вручную пользователем после приёмки; задание Windows тоже регистрирует пользователь.
17. Своего журнала запусков (`job_runs`) скрипт не ведёт: вывод идёт в `logs\mail.log`, единый журнал для всех скриптов — отдельный пункт бэклога.
